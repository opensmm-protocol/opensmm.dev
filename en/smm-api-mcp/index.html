SMM API for MCP

OpenSMM is an open protocol for ordering SMM services, and MCP is one of its transports. An MCP client connects to the /mcp endpoint of a gateway node (Streamable HTTP, header accept: application/json, text/event-stream) and gets the catalog, quotes and order execution through ten tools. Alongside runs the canonical REST binding /v0 — the same objects, the same rules.

Ten tools, one contract

get_capabilities

Protocol version, commands, payment methods, catalog version.

search_services

Find services by text, platform and goal.

get_service

Price and rate base, min/max, parameters, refill and cancel support.

get_quote

A quote with price and lead time. Required before ordering.

create_order

Idempotent order creation; replies with payment requirements.

get_order_status

Payment and execution statuses; safe to poll.

cancel_order

Cancellation where the service supports it.

request_refill

Refills on completed or partially completed orders.

list_providers

Pseudonymous nodes with gateway-measured metrics.

register_provider

Connect a provider — no applications, email or forms.

MCP and REST return the same objects

REST /v0 is the canonical HTTP binding of the protocol; MCP is an equal transport. The same operation via REST and via MCP returns the same domain objects. Idempotency is a protocol-level property: REST carries an Idempotency-Key header, MCP a clientReference field; repeating a request returns the same order. One clientReference → one orderId on any transport — an agent can mix MCP and REST without creating duplicates.

Amounts are decimal strings in integer micro-units, never floats. Error codes are canonical and identical on both transports: from VALIDATION_FAILED to IDEMPOTENCY_CONFLICT and INTERNAL.

How to wire up an agent

Point the MCP client at the gateway node address and call the tools in scenario order: get_capabilities → search_services → get_quote → create_order → pay per the requirements of the 402 response → get_order_status until COMPLETED. A quote is required before an order and is spent exactly once; the order replies with HTTP 402 carrying payment requirements — USDC on Base Sepolia (testnet), paid straight to the provider, bypassing the gateway.

The protocol spec, JSON schemas and call examples live in the spec/v0 directory of the repository; the MCP server manifest is mcp.json.

Where the services come from

A provider brings services into the node: an SMM panel connects with a single registration — baseUrl, apiKey and a behavior profile, no code (the smm-v2 adapter). Until a provider is connected the node serves a mock catalog: every service is marked "synthetic": true — fixtures for debugging an agent end-to-end, not a sellable offer. The site's public catalog is a demo snapshot of such a mock node.

Provider choice happens through list_providers: nodes are pseudonymous and the gateway measures quality on its own real orders — self-reports are banned. A new node starts as UNVERIFIED with a volume limit on orders; measured orders move it to ACTIVE. The quality formula is open, spec §9.1: you can recompute the numbers yourself.

The last step: run your own node

Your own gateway node is a single process serving REST /v0 and MCP /mcp on one port, with no keys and no external services. You need Node.js ≥ 22.18 — and nothing else.
