The open protocol for ordering SMM services

OpenSMM is a domain protocol for ordering and executing social-growth services by AI agents. Version 0.1.0, URL prefix /v0, MIT license. REST is the canonical HTTP binding; MCP is one inbound adapter. The same operation over both transports produces the same domain objects.

1. Who takes part

  • Gateway — the server agents talk to. It owns the catalog, quotes, prices, payments, idempotency, policy and refunds.
  • Provider — the execution supplier behind the Provider SPI. It knows nothing about MCP, x402 or clientReference.
  • Agent — the buyer. This version assumes a mock payment rail for local development.

The protocol is settlement-agnostic: payTo picks the topology. The canonical one is direct payment from agent to provider (x402, USDC on Base); money never transits a routing-only gateway. x402 payment is tested on the Base Sepolia testnet only; mainnet USDC is not enabled.

2. Models, not a single “status”

  • Service — a curated SKU; serviceId stays stable when the underlying provider changes. Price is a Money object with a decimal string, never a float.
  • Quote — a priced, expiring offer; mandatory before ordering, binding service, quantity, link and amount.
  • Order — the purchased execution with two independent statuses: paymentStatus and executionStatus.
  • PaymentIntent — the payment for an order, separated from Order so new rails do not change the lifecycle.
  • Capabilities — what a gateway supports: version, commands, payment methods, catalogVersion.

3. Two statuses instead of one

paymentStatus: REQUIRES_PAYMENT → VERIFYING → SETTLED (then REFUNDING/REFUNDED for refunds). SETTLEMENT_PENDING is not an error and not a reason to pay again.

executionStatus: NOT_STARTED → SUBMITTING → PENDING → IN_PROGRESS → COMPLETED. An ambiguous provider result becomes SUBMISSION_UNKNOWN; there is no blind resubmission.

4. Idempotency at the protocol level

The Idempotency-Key header (REST) or the clientReference field (MCP). Repeating the same key with the same payload returns the original order — no second charge, no second execution. The same key with different parameters returns IDEMPOTENCY_CONFLICT.

rule
one clientReference → one orderId on any transport

Provider APIs (SMM API v2) have no idempotency: after an ambiguous add result the order goes to SUBMISSION_UNKNOWN and is reconciled manually.

5. Protocol commands

REST / MCP
getCapabilities      GET  /v0/capabilities        get_capabilities
searchServices       GET  /v0/services             search_services
getService           GET  /v0/services/{id}        get_service
getQuote             POST /v0/quotes               get_quote
createOrder          POST /v0/orders               create_order
getOrder             GET  /v0/orders/{id}          get_order_status
cancelOrder          POST /v0/orders/{id}/cancel   cancel_order      — optional
requestRefill        POST /v0/orders/{id}/refill   request_refill    — optional
listProviders        GET  /v0/providers            list_providers
registerProvider     POST /v0/providers            register_provider — optional

Seven of ten are mandatory. Out of scope for 0.1: campaigns, subscriptions, mass orders, bargaining, auto-orders, account farms and A2A. For how MCP relates to REST see MCP for SMM panels.

Honest limits

  1. This page retells spec/v0 and docs/AGENT_QUICKSTART.md; exact schemas and statuses are there.
  2. The site and local node catalogs are mock (synthetic: true): no real services, prices or orders here, and the rates in examples are test ones.
  3. Breaking changes are allowed without notice until /v1; there is no SLA in 0.1.
