SMM panel connection profile

A profile is the data an OpenSMM node uses to describe your panel: baseUrl, apiKey, a behavior profile and a payout address. You write no integration code.

What a profile contains

  • adapter — your panel API dialect: smm-v2 (classic key + action) or rest-v1 (GET /services, POST /orders, Bearer auth).
  • endpoint / baseUrl — the public https:// URL of your panel API (SSRF guard, spec/v0 §10.2).
  • apiKey — your panel key. It is used only to call your API; it is never returned by the protocol, never logged, never shown in listings.
  • profile (smm-v2 only) — how your panel API differs from the classic shape: auth field, response envelope, field aliases.
  • payoutAddress — a USDC address on Base for direct payouts (optional but recommended).

How to get the profile

The doctor is a read-only check: HTTPS and JSON vs HTML/Cloudflare, action=balance, action=services, envelope and field aliases. Nothing is registered and the key is never printed. The report names a suggested profile and a ready connection snippet.

bash
OPENSMM_PANEL_KEY="<panel api key>" npm run doctor -- --url https://your-panel.example/api/v2

Exit code 0 — every check passed; 1 — the report names the failed check. The doctor speaks smm-v2 only; for rest-v1 the equivalent check is the gateway healthcheck at registration.

Register the panel

bash
curl -X POST http://localhost:8080/v0/providers \
  -H 'content-type: application/json' \
  -d '{
    "adapter": "smm-v2",
    "endpoint": "https://your-panel.example/api/v2",
    "apiKey": "<panel api key>",
    "profile": "<profile from the doctor report>",
    "payoutAddress": "0xYourUsdcAddressOnBase"
  }'

Re-registering the same endpoint is idempotent — you get the same providerKey. A ready placeholder template for rest-v1: examples/provider-profile.example.json. A filled file is a secret — keep it out of git and chats.

Honest limitations

  1. The npm package is not published yet: install from the repository checkout.
  2. You run and maintain the node yourself; it has no built-in TLS or authentication — see docs/DEPLOY.md.
  3. x402 payments are validated on USDC Base Sepolia — testnet.
  4. The public catalog is a demo (mock fixtures with synthetic: true) until the first panel connects.

The last step: run your own node

The node is a single process serving REST /v0 and MCP /mcp on one port. You need Node.js ≥ 22.18.
