Connect an SMM panel to AI agents

Your panel keeps working exactly as it does today — an OpenSMM node adds a second buyer to it. AI agents discover your services in the protocol catalog and order them over REST /v0 or MCP /mcp, and payment arrives straight at your address.

Connecting is data, not code: a baseUrl, an apiKey and a profile describing how the panel behaves. There is no integration to write — the panel serves orders through its usual API.

What connecting gives you

  • Agents see your services in the protocol catalog — with prices and quality the gateway measured on real orders, not on self-reports.
  • Orders arrive over two transports — REST /v0 and MCP /mcp. To the panel it is one order stream through the API it already has.
  • Payment — USDC via the x402 scheme — goes straight to your payout address. The gateway routes, quotes and measures, but money never passes through it and is never stored there.
  • The panel key is never returned, never logged and never shown in listings.

What you need to connect

  • baseUrl — the base URL of your panel's API speaking the classic smm-v2 dialect (key + action).
  • apiKey — a key that can read the service list and create orders.
  • profile — a description of how the panel's API differs from the classic shape. The doctor proposes the profile: it checks the API read-only — HTTPS, JSON, balance, catalog, response envelope, field aliases — and ships a ready profile in its report.
  • payoutAddress — a USDC address on Base for direct payouts (validated on Base Sepolia, testnet, today).

Three steps to connect

1. Check the panel API with the doctor

A read-only check: nothing gets registered, the key is never printed. The report contains a proposed profile and a ready-to-paste connection snippet.

bash
OPENSMM_PANEL_KEY="<panel key>" npm run doctor -- --url https://your-panel.example/api/v2

2. Register the panel as a provider

bash
curl -X POST http://localhost:8080/v0/providers \
  -H 'content-type: application/json' \
  -d '{
    "adapter": "smm-v2",
    "endpoint": "https://your-panel.example/api/v2",
    "apiKey": "<panel key>",
    "profile": "<profile from the doctor report>",
    "payoutAddress": "0xYourUsdcAddressOnBase"
  }'

The gateway validates the endpoint, healthchecks it by reading the service list and syncs the services into the node catalog.

3. Verify the node

bash
npm run verify:node -- <your node URL>   # exit 0 — the node passes the census

One order for every repeat

Idempotency lives at the protocol level, not in the panel. REST carries an Idempotency-Key header, MCP a clientReference field. Repeating a request returns the same order: one clientReference → one orderId on any transport. If an agent retries after a timeout, the order is not duplicated and the panel does not receive two orders instead of one.

An order has two independent state machines — paymentStatus and executionStatus. Payment and execution are tracked separately: the panel executes the order without waiting for the agent to stop polling payment.

Honest limitations

  1. No traffic guarantees. We cannot say when — or whether — agents will order.
  2. No SLA: the protocol is version 0.1.
  3. No hosting: you run and maintain the node yourself. The node has no built-in TLS or authentication — put a TLS proxy in front of it before publishing, see docs/DEPLOY.md.
  4. The npm package is not published yet: install from the repository checkout.
  5. x402 payments are validated on USDC Base Sepolia — testnet; mainnet is not enabled yet.
  6. The public catalog is a demo until the first panel connects. Your node starts as UNVERIFIED and moves to ACTIVE on measured orders.

The last step: run your own node

The panel connects to a node you run yourself. The node is a single process serving REST /v0 and MCP /mcp on one port, with no keys and no external services. You need Node.js ≥ 22.18 — and nothing else.
