Order SMM services through an AI agent

OpenSMM is an open protocol through which an AI agent discovers social growth services, requests a quote, creates an order and pays the executor directly. The agent works through MCP tools or plain HTTP: the step order and the objects are the same either way.

How an order goes

  1. Search. search_services finds offers by platform and goal across all connected nodes, with prices per thousand.
  2. Quote. get_quote pins the service, quantity, price and validity window. A quote is required before an order and is spent exactly once.
  3. Order. create_order is idempotent by clientReference and replies with HTTP 402 carrying payment requirements.
  4. Payment. The agent pays USDC on Base Sepolia (testnet) via the x402 scheme — straight to the provider address named in the requirements. The gateway holds no money.
  5. Tracking. get_order_status polls two independent statuses — payment and execution — until COMPLETED.

One clientReference → one orderId

Idempotency lives at the protocol level. REST carries an Idempotency-Key header, MCP a clientReference field. Repeating a request returns the same order: one clientReference → one orderId on any transport. The same operation via REST and via MCP yields the same domain objects, so an agent can mix transports freely without risking a second order.

A conflict is a distinct protocol error (IDEMPOTENCY_CONFLICT): the same idempotency key arrived with different parameters, and the agent gets an explicit refusal instead of a silently different order.

Money: straight to the provider, no middleman

The payment requirements in an order name the provider's own payout address — the agent pays it directly, via the x402 scheme. The gateway routes, quotes and measures quality — it is software, not a party to the deal: no balances, no custody of funds, no “merchant of record”. Settlements are validated today on USDC Base Sepolia (testnet); mainnet USDC on Base is not enabled yet.

Amounts in the protocol are decimal strings in integer micro-units, never floats: the agent loses nothing to rounding and can count money in integers.

Errors an agent handles

The error codes are canonical and identical on both transports — the agent handles them as an enumeration instead of parsing texts: VALIDATION_FAILED, NOT_FOUND, SERVICE_UNAVAILABLE, QUOTE_EXPIRED, QUOTE_MISMATCH, PAYMENT_REQUIRED, SETTLEMENT_PENDING, SUBMISSION_UNKNOWN, PROVIDER_REJECTED, POLICY_DENIED, IDEMPOTENCY_CONFLICT, REFUND_REQUIRED, INTERNAL.

Common cases: QUOTE_EXPIRED — the quote expired, request a new one; PAYMENT_REQUIRED — a normal step of an order, payment is not confirmed yet; SUBMISSION_UNKNOWN — the outcome of submitting the order to the provider is unknown (timeout): a blind retry is forbidden, reconcile to learn the outcome.

Where an agent gets services

The public catalog on the site is a demo snapshot of a mock node: every service is marked "synthetic": true — fixtures, not a sellable offer. An agent creates real orders on a node with a connected provider — an SMM panel or another supply node. Without a provider the node serves the mock catalog: a convenient way to run the agent end-to-end from search to status without making a single real order.

The last step: run your own node

To try the agent against a live protocol, run a gateway node: one process serves REST /v0 and MCP /mcp on one port, with no keys and no external services. You need Node.js ≥ 22.18 — and nothing else.
