Открытый протокол заказа SMM-услуг

OpenSMM — доменный протокол заказа и исполнения SMM-услуг для AI-агентов. Версия 0.1.0, URL-префикс /v0, лицензия MIT. REST — канонический HTTP-биндинг, MCP — один из входящих адаптеров; одна и та же операция по обоим транспортам даёт одни и те же объекты.

1. Кто участвует

  • Gateway (узел) — сервер, с которым говорят агенты. Держит каталог, котировки, цены, оплату, идемпотентность, политику и возвраты.
  • Provider (поставщик) — исполнитель за Provider SPI. Не знает ни про MCP, ни про x402, ни про clientReference.
  • Agent (агент) — покупатель. В этой версии assumed-mock платёжный контур для локальной разработки.

Протокол нейтрален к расчётам: payTo определяет схему. Каноническая — прямая оплата агентом поставщику (x402, USDC в Base), деньги не проходят через узел-маршрутизатор. Оплата по x402 проверена только в тестовой сети Base Sepolia; основная сеть не включена.

2. Модели, а не один «статус»

  • Service — редактируемый SKU; serviceId стабилен при смене провайдера. Цена — объект Money с десятичной строкой, не float.
  • Quote — ценовое истекающее предложение; обязательно до заказа, связывает услугу, количество, ссылку и сумму.
  • Order — купленное исполнение с двумя независимыми статусами: paymentStatus и executionStatus.
  • PaymentIntent — платёж по заказу, отделён от Order, чтобы новые способы оплаты не меняли жизненный цикл.
  • Capabilities — что поддерживает узел: версия, команды, способы оплаты, catalogVersion.

3. Два статуса вместо одного

paymentStatus: REQUIRES_PAYMENT → VERIFYING → SETTLED (далее REFUNDING/REFUNDED при возврате). SETTLEMENT_PENDING не ошибка и не повод платить повторно.

executionStatus: NOT_STARTED → SUBMITTING → PENDING → IN_PROGRESS → COMPLETED. Неопределённый ответ провайдера — SUBMISSION_UNKNOWN, слепой повторной отправки нет.

4. Идемпотентность на уровне протокола

Заголовок Idempotency-Key (REST) или поле clientReference (MCP). Повтор того же ключа с тем же телом возвращает исходный заказ — без второй оплаты и второго исполнения. Тот же ключ с другими параметрами даёт IDEMPOTENCY_CONFLICT.

rule
один clientReference → один orderId на любом транспорте

У провайдеров (SMM API v2) идемпотентности нет: после неоднозначного результата заказ уходит в SUBMISSION_UNKNOWN и сверяется вручную.

5. Команды протокола

REST / MCP
getCapabilities      GET  /v0/capabilities        get_capabilities
searchServices       GET  /v0/services             search_services
getService           GET  /v0/services/{id}        get_service
getQuote             POST /v0/quotes               get_quote
createOrder          POST /v0/orders               create_order
getOrder             GET  /v0/orders/{id}          get_order_status
cancelOrder          POST /v0/orders/{id}/cancel   cancel_order      — опц.
requestRefill        POST /v0/orders/{id}/refill   request_refill    — опц.
listProviders        GET  /v0/providers            list_providers
registerProvider     POST /v0/providers            register_provider — опц.

Обязательны семь из десяти. Вне версии 0.1: кампании, подписки, массовые заказы, торг, автозаказы, фермы аккаунтов и A2A. Как MCP связан с REST — MCP для SMM-панелей.

Честные ограничения

  1. Страница пересказывает spec/v0 и docs/AGENT_QUICKSTART.md; точные схемы и статусы — там.
  2. Каталог сайта и локального узла — mock (synthetic: true): реальных услуг, цен и заказов здесь нет, курс в примерах тестовый.
  3. До /v1 возможны несовместимые изменения без уведомления; SLA в 0.1 нет.

Дальше: поднять свой узел

Протокол оживает на узле. Поднимите локальный узел, пройдите путь «каталог → котировка → заказ → повтор» по гайду и сообщите адрес своего узла.

Пошаговый гайд — docs/AGENT_QUICKSTART.md; инструкция и проверка узла — на странице «Запустить узел».
