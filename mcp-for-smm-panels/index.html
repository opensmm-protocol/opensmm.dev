MCP for SMM panels

MCP is one inbound transport of OpenSMM; REST /v0 is the canonical HTTP binding. For an SMM panel this means: your API speaks one of the supported dialects, and joining a gateway is a single registerProvider call — no code.

1. MCP tools and their REST equivalents

The same operation over MCP and REST produces the same domain objects. The full 0.1 toolset:

MCP tool / REST
get_capabilities    GET  /v0/capabilities
search_services     GET  /v0/services
get_service         GET  /v0/services/{id}
get_quote           POST /v0/quotes
create_order        POST /v0/orders
get_order_status    GET  /v0/orders/{id}
list_providers      GET  /v0/providers
register_provider   POST /v0/providers     — optional
cancel_order        POST /v0/orders/{id}/cancel — optional
request_refill      POST /v0/orders/{id}/refill — optional

Idempotency in MCP is the clientReference field of create_order; in REST it is the Idempotency-Key header. One clientReference gives one orderId on any transport. See MCP vs REST and SMM API for MCP.

2. Supported panel dialects

  • smm-v2 — classic panel API: POST {endpoint} with key and action (services, add, status); behavior profiles handle panel deviations.
  • rest-v1 — reseller-style REST: GET {endpoint}/services, POST {endpoint}/orders, GET {endpoint}/orders/:id, Bearer auth.

Neither dialect requires you to write code: the gateway builds the adapter and syncs the catalog itself.

3. Check the panel before connecting

The doctor runs read-only Level-0 diagnostics: HTTPS and JSON instead of HTML/Cloudflare, action=balance and action=services with catalog size, envelope and field aliases, then a suggested profile and a ready connection snippet. Nothing is registered and the key is never printed.

bash
OPENSMM_PANEL_KEY="<your api key>" npm run doctor -- --url https://your-panel.example/api/v2

Exit code 0 — every check passed; 1 — the report names the failed check; use the suggested profile when registering. The doctor speaks smm-v2 only; for rest-v1 the gateway healthcheck plays that role. See panel and node check.

4. Register the panel

One register_provider (MCP) or POST /v0/providers (REST) call with the adapter, endpoint, apiKey and (optionally) a payout address. The apiKey is used only to call your API; it is never returned by the protocol, logged or shown in listings.

bash
curl -X POST https://<gateway>/v0/providers \
  -H 'content-type: application/json' \
  -d '{"adapter":"smm-v2","endpoint":"https://your-panel.example/api/v2","apiKey":"<your api key>"}'

Re-registering the same endpoint is idempotent — the same providerKey comes back. Publicly your panel is the pseudonym provider-beta; displayName is published only if you explicitly set publiclyListed. New nodes start UNVERIFIED with sampleSize: 0.

5. What happens under the hood

  1. SSRF guard — the endpoint must be a public https:// URL with no embedded credentials; loopback and private ranges are rejected.
  2. Healthcheck — the gateway lists your offers once, proving reachability, auth and catalog in one call.
  3. Catalog sync — offers appear in search_services under normalized IDs; catalogVersion changes on sync.
  4. Reputation — metrics are measured by the gateway from its own orders, never self-reported; the quality formula is open (spec/v0 §9.1).

With a payout address set, agents pay your panel directly (x402, USDC on Base) and money never transits the gateway. See connect an SMM panel and the connection profile.
