MCP для SMM-панелей

MCP — один из входящих транспортов OpenSMM; канонический HTTP-биндинг — REST /v0. Для панели это значит: её API говорят на одном из поддерживаемых диалектов, а подключение к гейтвею — один вызов registerProvider, без кода.

1. Инструменты MCP и REST-эквиваленты

Одна и та же операция по MCP и REST даёт одни и те же доменные объекты. Полный набор инструментов протокола 0.1:

MCP tool / REST
get_capabilities    GET  /v0/capabilities
search_services     GET  /v0/services
get_service         GET  /v0/services/{id}
get_quote           POST /v0/quotes
create_order        POST /v0/orders
get_order_status    GET  /v0/orders/{id}
list_providers      GET  /v0/providers
register_provider   POST /v0/providers     — опц.
cancel_order        POST /v0/orders/{id}/cancel — опц.
request_refill      POST /v0/orders/{id}/refill — опц.

Идемпотентность в MCP — поле clientReference в create_order; в REST — заголовок Idempotency-Key. Один clientReference даёт один orderId на любом транспорте. Разбор — MCP или REST и SMM API для MCP.

2. Поддерживаемые диалекты панели

  • smm-v2 — классический API панели: POST {endpoint} с key и action (services, add, status); профили поведений сглаживают отклонения панелей.
  • rest-v1 — реселлерский REST: GET {endpoint}/services, POST {endpoint}/orders, GET {endpoint}/orders/:id, авторизация Bearer.

Ни один из диалектов не требует от вас писать код: гейтвей сам строит адаптер и синхронизирует каталог.

3. Проверить панель до подключения

Doctor — read-only диагностика уровня 0: HTTPS и JSON вместо HTML/Cloudflare, проверка action=balance и action=services с размером каталога, конверт и псевдонимы полей, затем предлагаемый профиль и готовый сниппет подключения. Ничего не регистрируется, ключ не печатается.

bash
OPENSMM_PANEL_KEY="<your api key>" npm run doctor -- --url https://your-panel.example/api/v2

Код 0 — все проверки пройдены, 1 — в отчёте названа упавшая проверка; используйте предложенный profile при регистрации. Doctor говорит только на smm-v2; для rest-v1 роль проверки выполняет healthcheck гейтвея. См. проверка панели и узла.

4. Зарегистрировать панель

Один вызов register_provider (MCP) или POST /v0/providers (REST) с адаптером, endpoint, apiKey и (опционально) адресом выплат. apiKey нужен только для вызовов вашего API и никогда не возвращается протоколом, не логируется и не попадает в листинги.

bash
curl -X POST https://<gateway>/v0/providers \
  -H 'content-type: application/json' \
  -d '{"adapter":"smm-v2","endpoint":"https://your-panel.example/api/v2","apiKey":"<your api key>"}'

Повторная регистрация того же endpoint идемпотентна — вернётся тот же providerKey. Публично панель — псевдоним provider-beta; displayName публикуется, только если вы явно включили publiclyListed. Новый узел стартует с UNVERIFIED и sampleSize: 0.

5. Что происходит внутри

  1. SSRF-guard — endpoint обязан быть публичным https:// без встроенных credentials; петлевые и приватные диапазоны отклоняются.
  2. Healthcheck — гейтвей один раз запрашивает список предложений, подтверждая доступность, авторизацию и каталог.
  3. Catalog sync — предложения попадают в search_services под нормализованными ID; catalogVersion меняется при синхронизации.
  4. Репутация — метрики измеряет гейтвей по своим заказам, а не панель о себе; формула качества открыта (spec/v0 §9.1).

С адресом выплат агенты платят напрямую панели (x402, USDC в Base), деньги не проходят через гейтвей. Подробнее — подключить SMM-панель и профиль подключения.

Честные ограничения

  1. Страница пересказывает docs/PROVIDER_ONBOARDING.md, docs/AGENT_QUICKSTART.md и spec/v0; точные поля и версии — там.
  2. Каталог сайта и локального узла — mock (synthetic: true): реальных услуг, цен и заказов здесь нет; ключи и адреса в примерах — заглушки.
