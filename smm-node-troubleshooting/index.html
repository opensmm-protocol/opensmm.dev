Сбои запуска узла OpenSMM

Пять типовых сбоев при запуске узла из исходников: что вы увидите, почему так, как проверить и как исправить. Вывод взят из реальных локальных запусков.

1. Node.js старше 22.18

Узел запускает TypeScript напрямую, без компиляции. На старой версии Node.js процесс падает сразу, а npm ci печатает EBADENGINE.

text
TypeError [ERR_UNKNOWN_FILE_EXTENSION]: Unknown file extension ".ts" for /path/to/mcp-server/src/adapters/inbound/gateway.ts
bash
node -v   # нужно v22.18.0 или выше
bash
nvm install 22.18.0 && nvm use 22.18.0
# или с fnm:
fnm use 22.18.0

Причина: нативное удаление типов TypeScript доступно с Node.js 22.18.

2. Порт занят: EADDRINUSE

Порт по умолчанию — 8080. Если его держит другой процесс, узел падает с необработанным событием error.

text
Error: listen EADDRINUSE: address already in use :::8080
bash
lsof -i :8080
# или:
ss -tulpn | grep 8080
bash
PORT=8081 npm run gateway          # другой порт
node bin/opensmm.mjs gateway --port 0   # свободный порт выберет ОС

Остановить занявший порт процесс можно так: kill $(lsof -t -i :8080). С --port 0 узел напечатает выбранный порт в stderr.

3. Права на файл состояния: EACCES

Если OPENSMM_STATE_FILE (или --state) указывает туда, куда нельзя писать, сохранение снимка падает. Если у файла нет прав на чтение, узел молча стартует с пустым состоянием и не восстанавливает заказы, метрики и узлы.

text
Error: EACCES: permission denied, open '/root/.opensmm-state.json.tmp-1244552'
bash
ls -la "$OPENSMM_STATE_FILE"
ls -la "$(dirname "$OPENSMM_STATE_FILE")"
bash
touch "$OPENSMM_STATE_FILE"
chmod 600 "$OPENSMM_STATE_FILE"
chown $(id -u):$(id -g) "$OPENSMM_STATE_FILE"

Обычная причина: файл или каталог принадлежит root после прошлого запуска в Docker. Снимок содержит учётные данные провайдера и пишется с правами 0600.

4. npm ci без сети

npm ci скачивает пакеты из package-lock.json. Без доступа к реестру установка не пройдёт.

text
npm error code ECONNREFUSED
npm error code ENOTFOUND
npm error code ENOTCACHED
bash
curl -I https://registry.npmjs.org
npm ping
npm config get proxy
npm config get https-proxy
bash
npm ci --prefer-offline   # если пакеты заранее лежат в ~/.npm

В изолированной среде заранее прогрейте кэш на машине с интернетом. В Docker проверьте, что у контекста сборки есть доступ в сеть или локальное зеркало.

5. Каталог пустой или целиком synthetic

Если не заданы обе переменные OPENSMM_REST_V1_BASE_URL и OPENSMM_REST_V1_API_KEY, узел работает на встроенном mock-каталоге: все услуги с "synthetic": true, провайдер provider-alpha, а фильтр по платформе вне набора (например ?platform=twitter) возвращает {"services":[]}. Заказы по mock-услугам живут только в памяти и никуда не отправляются.

stderr
OpenSMM 0.1.0 gateway listening on http://localhost:8080 (REST /v0, MCP /mcp; provider: mock, mock catalog — not real supply)
bash
curl -s http://localhost:8080/v0/providers | grep '"synthetic":true'
env | grep OPENSMM_REST_V1
bash
export OPENSMM_REST_V1_BASE_URL="https://provider.example/api/v1"
export OPENSMM_REST_V1_API_KEY="your-api-key"
npm run gateway

Для панелей SMM API v2 сначала запустите диагностику: OPENSMM_PANEL_KEY="YOUR_KEY" npm run doctor -- --url https://panel.example/api/v2. Ключ берётся из переменной окружения и не попадает в argv. Подробнее — проверка панели и узла: doctor.

Честные ограничения

  1. Страница пересказывает docs/TROUBLESHOOTING.md репозитория mcp-server; полный текст и вывод — там.
  2. Mock-каталог — это фикстуры (synthetic: true), а не реальное предложение: живой провайдер подключается отдельным шагом.
  3. Пакет npm и публичный образ не опубликованы: узел собирается из чекаута репозитория.
