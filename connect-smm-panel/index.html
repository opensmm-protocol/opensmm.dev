Подключить SMM-панель к AI-агентам

Ваша панель продолжает работать как раньше — узел OpenSMM добавляет к ней второго покупателя. AI-агенты находят ваши услуги в каталоге протокола и заказывают их через REST /v0 или MCP /mcp, а оплата приходит напрямую на ваш адрес.

Подключение — это данные, а не код: baseUrl, apiKey и профиль поведения панели. Писать интеграцию не нужно — панель отдаёт заказы через свой обычный API.

Что даёт подключение

  • Агенты видят ваши услуги в каталоге протокола — с ценами и качеством, которое гейтвей измерил по реальным заказам, а не по самоотчётам.
  • Заказы приходят по двум транспортам — REST /v0 и MCP /mcp. Для панели это один поток заказов через существующий API.
  • Оплата — USDC по схеме x402 — уходит напрямую на ваш адрес выплат. Гейтвей маршрутизирует, котирует и измеряет, но деньги через него не проходят и у него не хранятся.
  • Ключ панели не возвращается, не логируется и не показывается в списках.

Что нужно для подключения

  • baseUrl — базовый URL API вашей панели, говорящей на классическом диалекте smm-v2 (key + action).
  • apiKey — ключ, который умеет читать список услуг и создавать заказы.
  • профиль — описание того, чем API панели отличается от классической формы. Профиль подсказывает доктор: он проверяет API только на чтение — HTTPS, JSON, баланс, каталог, конверт ответа, псевдонимы полей — и в отчёте предлагает готовый профиль.
  • payoutAddress — адрес USDC на Base для прямых выплат (сегодня проверяется на Base Sepolia, testnet).

Три шага подключения

1. Проверьте API панели доктором

Проверка только на чтение: ничего не регистрируется, ключ не печатается. В отчёте — предложенный профиль и готовый сниппет подключения.

bash
OPENSMM_PANEL_KEY="<ключ панели>" npm run doctor -- --url https://your-panel.example/api/v2

2. Зарегистрируйте панель как провайдера

bash
curl -X POST http://localhost:8080/v0/providers \
  -H 'content-type: application/json' \
  -d '{
    "adapter": "smm-v2",
    "endpoint": "https://your-panel.example/api/v2",
    "apiKey": "<ключ панели>",
    "profile": "<профиль из отчёта доктора>",
    "payoutAddress": "0xВашАдресUsdcНаБазе"
  }'

Гейтвей проверяет endpoint, делает healthcheck чтением списка услуг и синхронизирует их в каталог узла.

3. Проверьте узел

bash
npm run verify:node -- <URL вашего узла>   # exit 0 — узел проходит ценз

Один заказ на любой повтор

Идемпотентность — на уровне протокола, а не панели. REST передаёт заголовок Idempotency-Key, MCP — поле clientReference. Повтор запроса возвращает тот же заказ: один clientReference → один orderId на любом транспорте. Если агент повторит вызов после таймаута, заказ не задублируется, и панель не получит два заказа вместо одного.

У заказа два независимых автомата состояний — paymentStatus и executionStatus. Оплата и исполнение отслеживаются отдельно, панель исполняет заказ, не дожидаясь, пока агент перестанет опрашивать оплату.

Честные ограничения

  1. Нет гарантий трафика. Мы не можем сказать, когда и будут ли агенты заказывать.
  2. Нет SLA: протокол — версия 0.1.
  3. Нет хостинга: узел вы запускаете и обслуживаете сами. У узла нет своего TLS и аутентификации — перед публикацией поставьте TLS-прокси, см. docs/DEPLOY.md.
  4. Пакет npm ещё не опубликован: установка из чекаута репозитория.
  5. Платежи x402 проверяются на USDC Base Sepolia — testnet; mainnet пока не включён.
  6. Публичный каталог — демонстрация, пока первая панель не подключена. Ваш узел стартует со статусом UNVERIFIED и переходит в ACTIVE по измеренным заказам.

Последний шаг: поднять свой узел

Панель подключается к узлу, который вы запускаете сами. Узел — один процесс, отдающий REST /v0 и MCP /mcp на одном порту, без ключей и внешних сервисов. Нужен Node.js ≥ 22.18 — и ничего больше.
