Заказ SMM-услуг через ИИ-агента

OpenSMM — открытый протокол, по которому ИИ-агент находит услуги роста соцсетей, запрашивает котировку, создаёт заказ и оплачивает его напрямую исполнителю. Агент работает через MCP-инструменты или обычный HTTP: порядок шагов и объекты одни и те же.

Как проходит заказ

  1. Поиск. search_services находит предложения по платформе и цели на всех подключённых узлах, с ценами за тысячу.
  2. Котировка. get_quote фиксирует услугу, количество, цену и срок действия. Котировка обязательна перед заказом и расходуется ровно один раз.
  3. Заказ. create_order идемпотентен по clientReference и отвечает HTTP 402 с требованиями к оплате.
  4. Оплата. Агент платит USDC на Base Sepolia (testnet) по схеме x402 — напрямую на адрес провайдера из требований. Гейтвей деньги не держит.
  5. Отслеживание. get_order_status опрашивает два независимых статуса — оплату и исполнение — до COMPLETED.

Один clientReference → один orderId

Идемпотентность — на уровне протокола. REST передаёт заголовок Idempotency-Key, MCP — поле clientReference. Повтор запроса возвращает тот же заказ: один clientReference → один orderId на любом транспорте. Одна и та же операция через REST и MCP даёт одни и те же доменные объекты, поэтому агент может свободно смешивать транспорты, не рискуя создать второй заказ.

Конфликт — отдельная ошибка протокола (IDEMPOTENCY_CONFLICT): тот же ключ идемпотентности пришёл с другими параметрами, и агент получает отказ явно, а не молча другой заказ.

Деньги: прямо провайдеру, без посредника

Требования к оплате в заказе называют адрес выплат самого провайдера — агент платит ему напрямую, по схеме x402. Гейтвей маршрутизирует, котирует и измеряет качество — это ПО, а не сторона сделки: без балансов, без хранения средств, без «мерчанта записи». Расчёты сегодня проверяются на USDC Base Sepolia (testnet); mainnet USDC на Base пока не включён.

Суммы в протоколе — десятичные строки в целых микро-единицах, никогда float: агент не теряет копейки на округлении и может считать деньги в целых числах.

Ошибки, которые агент обрабатывает

Коды ошибок канонические и одинаковые на обоих транспортах — агент обрабатывает их как перечисление, а не парсит тексты: VALIDATION_FAILED, NOT_FOUND, SERVICE_UNAVAILABLE, QUOTE_EXPIRED, QUOTE_MISMATCH, PAYMENT_REQUIRED, SETTLEMENT_PENDING, SUBMISSION_UNKNOWN, PROVIDER_REJECTED, POLICY_DENIED, IDEMPOTENCY_CONFLICT, REFUND_REQUIRED, INTERNAL.

Частые случаи: QUOTE_EXPIRED — котировка истекла, запросите новую; PAYMENT_REQUIRED — нормальный шаг заказа, оплата ещё не подтверждена; SUBMISSION_UNKNOWN — результат отправки заказа провайдеру неизвестен (таймаут): слепой повтор запрещён, исход уточняется сверкой.

Где агент берёт услуги

Публичный каталог на сайте — демонстрационный снапшот mock-узла: каждая услуга помечена "synthetic": true, это fixtures, а не продаваемое предложение. Реальные заказы агент создаёт на узле, к которому подключён поставщик — SMM-панель или другой узел поставок. Поставщика нет — узел отдаёт mock-каталог: на нём удобно прогнать агента от поиска до статуса end-to-end, не сделав ни одного реального заказа.

Последний шаг: поднять свой узел

Чтобы опробовать агента на живом протоколе, поднимите узел гейтвея: один процесс отдаёт REST /v0 и MCP /mcp на одном порту, без ключей и внешних сервисов. Нужен Node.js ≥ 22.18 — и ничего больше.
