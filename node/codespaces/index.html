Run a node in GitHub Codespaces

No server of your own, no Docker, no domain. A GitHub Codespace is a ready Linux machine in the browser: open the protocol repository, start the gateway, and expose it on a public URL through port forwarding. The node serves REST /v0 and MCP /mcp on one port — and its catalog is the demo mock catalog until you connect a real provider.

1. Open the repository in Codespaces

Open opensmm-protocol/mcp-server on GitHub, press Code, switch to the Codespaces tab and click Create codespace on main. The first launch takes a minute while the container is built. The repository ships a devcontainer configuration, so the codespace comes with the right Node.js (≥ 22.18) out of the box — the full walkthrough lives in docs/CODESPACES.md. A free GitHub account is enough; Codespaces runs within its free monthly allowance (current limits are in GitHub's own docs).

Open the repo on GitHub

If you reuse an existing codespace, run node -v first — the gateway needs Node.js ≥ 22.18 (native TypeScript type stripping without flags).

2. Install dependencies

In the codespace terminal, install the dependencies with npm ci.

bash
npm ci

3. Start the gateway node

Launch the gateway on port 8080. By default it boots against the built-in MockProvider catalog — no keys and no external services.

bash
PORT=8080 npm run gateway

The node reports its listening port on stderr:

stderr
OpenSMM 0.1.0 gateway listening on http://localhost:8080 (REST /v0, MCP /mcp; provider: mock, mock catalog — not real supply)

4. Forward port 8080 and make it public

When the gateway starts listening, Codespaces forwards port 8080 automatically. Open the Ports panel in the codespace, find port 8080 and switch its visibility to Public. Codespaces gives the forwarded port a stable public URL of the form:

url
https://<codespace-name>-8080.app.github.dev

That URL is all you need to point agents and MCP clients at your node. It stays live while the codespace runs and goes down when the codespace stops — Codespaces is the five-minute path; a permanent deployment is covered in docs/DEPLOY.md.

5. Verify the node (REST and MCP)

Check that your node answers on both transports over the public URL. Check GET /v0/services to inspect the catalog and POST /mcp for JSON-RPC MCP initialization.

bash
curl -s -o /dev/null -w '%{http_code}\n' https://<codespace-name>-8080.app.github.dev/v0/services   # 200
curl -s https://<codespace-name>-8080.app.github.dev/v0/services | head -30   # every service has "synthetic": true
curl -s -X POST https://<codespace-name>-8080.app.github.dev/mcp \
  -H 'content-type: application/json' -H 'accept: application/json, text/event-stream' \
  -d '{"jsonrpc":"2.0","id":1,"method":"initialize","params":{"protocolVersion":"2025-06-18","capabilities":{},"clientInfo":{"name":"qa","version":"1"}}}'   # serverInfo.name = "opensmm"

The catalog you see is the demo mock catalog, not real supply: the gateway runs without a provider key, so every service carries "synthetic": true — these are fixtures to exercise the protocol end to end, with no real orders and no real balances. Services and prices on it are samples, not sellable supply. The live catalog appears only when you connect a real provider (an SMM panel) to the gateway via OPENSMM_REST_V1_*.

Your node is live

Both checks return 200 — your node is on the air. The full guide covers the node definition, the census that counts it, and node reporting to the network.
